# 内核迁移说明：从自研单循环换成 LangChain / LangGraph

2026-11-20。对应《Agent架构与选型.md》3.2 节和第 11 节阶段 1。

**现状：代码写完了，但还没有在装了 LangChain / LangGraph 的机器上跑过。** 开发环境不能联网装包。第一次真正运行在你的电脑上，步骤见第 7 节。

## 1. 改了什么

只换中间那层。界面、业务工具、HTTP 接口、账本里的事件和任务状态都不变，`agent/server.py` 和 `ui/` 没有改。

| 文件 | 内容 |
|---|---|
| `agent/lg/__init__.py` | `available()`：只做导入检查，决定能不能用新内核 |
| `agent/lg/models.py` | ChatOpenAI 的建法；测试和演示用的假模型 `ScriptedChatModel`；流式片段转发 `DeltaHandler`；消息格式互转 |
| `agent/lg/tools.py` | 业务工具包成 `StructuredTool`；连接器用 langchain-mcp-adapters |
| `agent/lg/kernel.py` | 每次运行的内核：批准判定、执行工具前后记账、问模型（可打断）、提问、插话补齐、压缩记账 |
| `agent/lg/middleware.py` | 我们的 `KernelMiddleware` 加官方中间件，组装成 `create_agent` 的 middleware 列表 |
| `agent/lg/host.py` | 宿主：SQLite 检查点、任务线程主循环、子代理 |
| `agent/runtime.py` | 按配置 `kernel` 选内核；设置 `kernel_name`；几处转给新内核（任务线程、子代理、连接器、删任务、关闭） |
| `agent/__main__.py` | 启动时打印用的是哪个内核；`kernel=langgraph` 但用不了时报清楚的错并退出 |
| `tests/helpers.py` | 旧内核的测试固定用旧内核；加了 `lg_env()` 和 `HAS_LG` |
| `tests/test_lg_loop.py`、`test_lg_recovery.py`、`test_lg_context.py` | 新内核的行为测试（移植自 test_loop、test_recovery、test_context、test_mcp），没装包时跳过 |
| `tests/lg_smoke.py` | 逐项自检：一步一步验证对官方接口的每个假设 |
| `tests/run_lg_tests.sh` | 建 `.venv`、装依赖、跑自检和全部测试、试启动，结果写到 `tests/results/lg_run.txt` |

旧内核（`agent/loop.py`、`agent/context.py`、`agent/llm.py`、`agent/mcp.py`）和它的测试原样保留，新内核在真机上验证通过后再退役。新内核也复用了旧内核的一些纯函数和文字（`context.system_prompt`、`context.project`、`loop` 里的结果文字、`mcp.tool_name`），退役时要把这些搬走。

### 怎么选内核

配置项 `kernel`（`settings.json`）：

- `auto`（默认）：`agent.lg.available()` 为真就用新内核；否则用旧内核，每个任务第一次运行时发一条 notice："没有安装 LangChain / LangGraph，当前使用过渡内核。安装方法：pip install -r requirements.txt"，终端也打印原因。
- `langgraph`：用不了就在启动时报错退出，并说明缺什么。
- `builtin`：一直用旧内核。

`Runtime.kernel_name` 是 `"langgraph"` 或 `"builtin"`，`/api/state` 已经带上了它。

## 3. 设计要点

### 3.1 账本和检查点

- **账本**（`ledger.db` 的 events、actions、audit）仍是界面和审计的事实来源，事件类型和载荷与旧内核相同。
- **检查点**（`checkpoints.db`）里的消息是给模型看的上下文。
- 两边由内核保持一致：每次模型回复写 `assistant_message`（调用 id 在任务内去重，解析失败的调用也记进去）；每个工具结果写 `tool_result`；图里有、账本里没有的结果（批准中间件的拒绝、计划中间件的并行报错）在下一个钩子里补记。
- 会话 meta 里多了 `lg_fed`：已经交给图的最后一条 `user_message` 的 seq。比它新的就是"用户插话"。

### 3.2 批准（官方中间件 + 动态条件）

我们的批准是动态的：同一个 `write_file`，新建不问、覆盖要问；删除永远问；还受批准模式和每个工具的设置影响（`policy.decide` 和工具的 `risk_of`）。

官方文档说明 `InterruptOnConfig` 有 `when`：收到 `ToolCallRequest`，返回真就停下来问，假就自动放行，**要求恢复时结果不变**（langchain>=1.3.3）。所以用官方中间件，`when` 指向 `kernel.gate`：

- 第一次判定时在 actions 表登记动作（`awaiting` / `approved` / `denied`），要问的发 `approval_requested`；
- 恢复时重算：发过批准请求的一律返回真，判定过的不再变。这样满足"恢复时结果不变"。
- 用户在界面点批准或拒绝仍走 `Runtime.decide`（改 actions 表）。主循环看到这一批都决定了，用 `Command(resume={中断id: {"decisions": [...]}})` 恢复；拒绝的决定带上我们的文字作为 `message`。
- 执行前再核一次：动作状态、修订号、参数要和批准时一致（批准绑定具体动作）；自动放行的调用执行前重新判一次风险（例如同一条回复里先新建、再写同一个文件，第二次已经是覆盖），需要问就不执行，告诉模型"请再调用一次"，下一轮会正常走批准。

和旧内核的差别：官方中间件是"一轮一次"（batched），一条回复里有几个要批准的调用就同时发出几个批准请求，都决定了才继续；旧内核是一个一个问。批准前这一轮什么都不执行（旧内核会先执行前面不用批准的调用）。同一批里对某工具点了"以后都允许"，同工具的其他待批准一并放行。

### 3.3 提问

`ask_user` 的调用在我们自己的 after_model 钩子里用 `interrupt()` 停下，界面照旧收到 `question` 事件；回答记成 `answer` 事件后用 `Command(resume=…)` 恢复，工具执行时从账本取答案。放在 after_model 而不是工具里，是因为 LangGraph 会把同一条回复里的多个工具调用并行执行，工具里停下来会和其他并行的调用纠缠；after_model 只有一个节点，顺序确定。一个节点里多次 `interrupt()` 按调用次序匹配恢复值（官方文档原话），代码按这个规则写。

### 3.4 结果未知时不重做

官方文档：恢复时被中断的节点从头再跑。每个有副作用的工具执行前把动作置为 `running` 并落盘，执行后置为 `done` / `failed` 并存结果（以 tool_call_id 为键）。节点重跑时：

- 账本里已有这次调用的 `tool_result` 或动作已 `done` / `failed` → 照抄结果，不执行；
- 动作是 `running` 且本进程里确实还在执行（另一个线程）→ 等它做完再照抄；
- 动作是 `running` 但没人在执行（进程重启过）→ 置为 `unknown`，返回"此动作在执行中途程序中断，结果未知。不要重做……"。

### 3.5 中途改要求

- **正在调用模型时插话**：`call_model` 在一个工作线程里调用模型，本线程每 50 毫秒看一眼取消事件（`Runtime.send_message` 会触发它）。被打断就丢下工作线程（它的回复和流式片段都被忽略），抛 `Abort` 结束这次运行。LangGraph 的同步运行没办法从外面打断正在执行的节点，所以只能这样。主循环随后带上新消息开始新的一次运行。
- **等批准时插话**：`Runtime.send_message` 照旧把待批准的动作置为 `voided`。主循环不恢复那次中断，而是给新输入：先按账本给没结果的调用补上"未执行：用户更改了要求"，再加上新的用户消息。LangGraph 收到新输入时会丢弃上次没跑完的任务（源码 `pregel/_loop.py` 的注释 "discard any unfinished tasks from previous checkpoint"）。
- **工具执行中插话**：已经在做的如实记录，后面没做的作废。
- 给模型的每条带调用的回复后面紧跟它全部的工具结果（按调用顺序排），新消息在最后。

### 3.6 同一条回复里的多个工具调用

`create_agent` 对每个调用发一个 `Send("tools", [tool_call])`，并行执行。我们按模型给出的顺序一个一个做（例如先写文件再读同一个文件）：每个调用先等前面的调用在账本里有结果。前面的调用 10 秒还没开始（理论上不会），就不再等，避免卡死。

### 3.7 重启

- `recover()` 不变：活动任务置为暂停。打开历史任务不调用模型、不执行动作。
- 用户点继续：主循环看检查点——停在中断上就接着等同一个批准或回答；上次运行没跑完就 `invoke(None)` 接着跑；有插话就带新消息开始。
- 旧内核留下的任务（没有检查点）：第一次在新内核上继续时，按旧规则补齐没结果的调用，再把账本投影成消息作为输入。

### 3.8 预算和失败

- 步数：`ModelCallLimitMiddleware` 和 `ToolCallLimitMiddleware` 用 `exit_behavior="error"`，抛异常后任务暂停（"步数用尽"）并发 notice。**注意：官方的"单次运行"计数在每次 invoke 时重置，而批准、回答之后的恢复都是新的一次 invoke**，所以步数上限管的是"两次人工操作之间"的步数。每次都要人点，不会无限跑。
- 连续失败、空回复、总时长：沿用旧内核的计数（用户发消息或点继续时清零），到上限暂停。
- 模型不可用（重试和换台之后仍失败）：发 error，暂停（"模型不可用：…"）。点继续时从检查点接着问。
- LangGraph 默认的递归上限是 25 个超步，不够，设成 100000，步数交给上面的中间件管。

## 4. 没用官方部件的地方和原因

| 地方 | 做法 | 原因 |
|---|---|---|
| 提问 | 自己的 after_model 钩子里调 `interrupt()` | 官方 HITL 的 `respond` 决定是"不执行工具、直接把回答当结果"，可以用，但它和批准共用一个中断、一轮一次；我们需要提问卡片、答案事件、暂停后用普通消息作答等现有行为，放在独立钩子里更清楚。仍是官方的 `interrupt()` |
| 子代理 | 子代理作为工具（LangChain 文档"subagents"一节的写法） | Deep Agents 的 `SubAgentMiddleware` 默认会加一个"通用子代理"，继承主代理的全部工具（还带文件系统工具），要关掉得改 harness profile；文档也没说它能脱离 `create_deep_agent` 单独用。我们要求子代理只能拿到 `sub_ok=True` 的只读工具、在账本里是一个子任务、主任务暂停或改要求时跟着停，自己写更可控。另外 deepagents 又多一组依赖 |
| 技能 | 保留 `skill_load` | Deep Agents 的 `SkillsMiddleware` 通过 backend 的 `read_file` 读 SKILL.md，会和我们自己的 `read_file`（带路径守卫、只能读工作区）冲突；技能目录在程序目录和数据目录，不在工作区里 |
| 连接器工具 | 适配器拿到的工具再包成我们的 `Tool` | 让连接器和业务工具走同一条批准、记账、审计的路（风险一律"对外"）；适配器的工具只有异步实现，我们在线程里用独立事件循环调用 |
| 打断模型调用 | 工作线程 + 丢弃 | LangGraph 同步运行没有从外部取消正在执行的节点的接口 |
| 权限、记账、"结果未知时不重做" | 自己的 wrap_tool_call | 业务本身，框架不提供（架构文档 3.2 也这么写） |

## 6. 没有运行验证过的地方（最可能出错的排前面）

括号里是 `tests/lg_smoke.py` 里对应的自检步骤。

1. **批准中间件的 `when` 条件**（需要 langchain>=1.3.3）：恢复时会再调用一次 `when`，我们靠账本保证结果不变；中断内容和恢复值的格式按文档写。如果 `when` 的签名或批量模式的行为和文档不同，批准会整个失效或卡住（步骤 03、09、10）。
2. **在工作线程里调用模型**：`wrap_model_call` 把 `handler(request)` 放到另一个线程里跑（`contextvars.copy_context()` 带上 LangGraph 的上下文）。如果 LangGraph 的某些内部状态不能跨线程，模型调用会报错。备选方案：不打断，等模型返回后再丢弃（插话和暂停会慢一些）（端到端步骤 22，以及全部 test_lg_* 测试）。
3. **并行的工具任务和我们的排序等待**：前提是 LangGraph 把同一条回复的多个调用放在不同线程里并行跑，或者按顺序跑。如果它按别的方式调度，可能出现 10 秒的等待（步骤 08 会打印实际的开始顺序和线程）。
4. **停在中断上时给新输入**：源码说会丢弃没跑完的任务，但中断记录本身是否也随之失效没有明说（步骤 13）。
5. **`ScriptedChatModel`（假模型子类）**：是 pydantic 模型，自定义字段 `backend`、`specs`；`disable_streaming=True` 让它不走父类的流式实现。字段或校验规则不同会导致所有新内核测试都起不来（步骤 04）。
6. **压缩**：`token_counter` 用旧内核的估算；`trigger`、`keep` 都按 token；摘要请求的提示词用我们的中文提示词加 `{messages}`。触发后摘要模型调用失败会让任务按"模型不可用"暂停，没有旧内核那样的机械摘要兜底（步骤 16，测试 LGCompression）。
7. **计划中间件把系统消息改成内容块列表**：发给 vLLM 的 system 消息 content 是数组。vLLM 一般能处理，但没在你们的 vLLM 上试过（步骤 17 只能看到假模型收到的格式，真实效果要跑 `tests/realmodel/`）。
8. **ChatOpenAI 的参数**：`http_client=httpx.Client(trust_env=False)` 让内网端点不走系统代理；`max_tokens` 新版本可能以 `max_completion_tokens` 发出，需要 vLLM 支持；`stream_usage=True`；`use_responses_api=False`（步骤 19 只检查对象，不联网）。
9. **模拟崩溃的测试手法**：工具里抛 `BaseException` 的子类，假设它会一路冲出 LangGraph，留下停在工具节点上的检查点。如果 LangGraph 吞掉或转换了它，test_lg_recovery 里三个"崩溃"测试会失败，但这只说明测试手法要改，不一定是内核的问题。
10. **`StructuredTool` + dict 参数格式经过 ToolNode**：ToolNode 检测注入参数时会看工具的参数格式（步骤 05、06）。
11. **SqliteSaver 跨线程**：用一条 `check_same_thread=False` 的连接给所有任务线程共用，假设 SqliteSaver 自己有锁。`setup()`、`delete_thread()` 不存在时跳过（步骤 12）。
12. **`invoke(..., durability="sync")`**：参数存在才传（步骤 20）。
13. **连接器**：`handle_tool_errors=False` 的构造参数（不认就退回默认，此时连接器报错会被当成成功的结果）；测试用的假服务启动时先打印一行非 JSON，官方 MCP SDK 是否容忍没试过（步骤 21）。每次调用都会新起一次服务进程，慢。
14. **步数上限的计数范围**：见 3.8，单次 invoke 内计数。
15. **依赖的最低版本**：`requirements.txt` 里的下限是按文档推的（`when` 需要 langchain 1.3.3），没有逐个版本试过。pip 会装最新版。

另外，**本机自检的局限**：开发环境里写了一个只模拟这些接口"文档上说的行为"的本地桩（不在项目里），用它跑通了全部新内核测试（41 个，连跑 5 次稳定）和自检脚本的大部分步骤。这只能说明我们自己的胶水代码（主循环、记账、线程、各种分支）逻辑通顺，不能说明对官方接口的理解是对的。

**新接的部分和它依赖的假设**

1. **工具结果里的结构化数据**（`hits`、`display`、`open`、`used`）：处理函数返回 `tools.WithData`（`str` 的子类，带 `extra`）。`lg/tools._runner` 把 `extra` 记进 `kernel.extras[调用 id]`（和截图同一条路），`kernel.write_result` 并进 `tool_result` 的 payload；`kernel.execute` 还把它存进动作的 `result.extra`，重启后补写结果时带上（`run_tool` 里 `done/failed` 的分支、`reconcile` 里补结果的分支）。假设和截图一样：调处理函数时 `kernel.ctx.call_id` 已经设好。`to_text(WithData)` 原样返回文字，所以 ToolMessage 的内容就是给模型看的那段文字。
2. **"对话里只留最近两次检索的全文"**：在 `kernel.prune_pages(request)` 开头做（同一个 `wrap_model_call`，在 `prune_images` 之后）：`ToolMessage.name` 是 `kb_search` / `kb_open`、而且内容里有"以下是资料内容……"那行标记的，除了最后两条都换成"（更早的检索结果已省略，需要时重新检索）"。只改这一次请求。假设同第 10 节第 2 条（`ToolMessage.name` 是工具名、`model_copy` 可用）。
3. **编号**：`kb_search` 的编号从账本里算（`kb.cite_map`：这个对话和它的子代理的 `tool_result.hits`），不依赖检查点。新内核下 `tool_result` 一样写账本，所以重启、换内核都不会乱。
4. **`kb.engine=langchain`**（`agent/kb/vectors.py` 的 `LangchainVectors`）用到的接口：
   - `langchain_chroma.Chroma(collection_name="kb", embedding_function=…, persist_directory=<数据目录>/chroma, collection_metadata={"hnsw:space": "cosine"})`；`add_texts(texts, metadatas=[{"library_id", "doc_id", "part_id"}], ids=[str(part_id)])`；`delete(ids=[…])`；`reset_collection()`；`similarity_search_with_relevance_scores(问题, k=, filter={"library_id": {"$in": [...]}})`；`as_retriever(search_type="similarity", search_kwargs={"k", "filter"})`。假设 Chroma 的 `filter` 认 `$in`（chromadb 0.4 起的写法）、元数据里的整数原样存回。
   - `langchain_openai.OpenAIEmbeddings(model=, base_url=, api_key=, check_embedding_ctx_length=False, chunk_size=batch, dimensions=dims?)`：接 vLLM 时一定要关掉按 token 切分（否则它会先用 tiktoken 把文字切成 token id 发过去，vLLM 的 Qwen3-Embedding 不认）。`query_prefix` 只加在问题上：子类化 `OpenAIEmbeddings`，只改 `embed_query`（`embed_documents` 不动）。
   - 检索时**融合用的是我们自己的按名次融合**（RRF，k=60），而不是 `langchain_classic.retrievers.EnsembleRetriever`：原因是要知道每个命中是哪一路找到的（`via`）、要把 1 到 3 种问法的名单一起融合（9.2），EnsembleRetriever 两样都给不出。算法和 EnsembleRetriever 的加权 RRF 一样（权重各 0.5 时名次完全一致）。`langchain-classic` 仍在依赖里，`kb_lc_smoke.py` 检查它能导入；如果要换成 EnsembleRetriever，关键词那一路包成 `BaseRetriever` 子类（`_get_relevant_documents` 调 `retrieve.keyword`）即可。
   - `kb_vectors` 表照样记一行（`vec` 为空），用来数"有多少片段有向量"和找"缺向量的片段"；向量本身只在 Chroma 里。
   - `kb.engine=auto` 时装齐 `langchain_chroma`、`langchain_openai`、`langchain_classic`、`chromadb` 四个包才用这一套，否则用 builtin（SQLite + numpy）；写了 `langchain` 而没装齐也退回 builtin（不报错，`/api/capabilities` 的 `embedding.kb_engine` 写的是实际用的那套）。
5. **已知的出入**：语义检索的"在不在线"是用到时才知道的（收录或检索时调一次向量模型，成功记"在线"，失败记"连不上"）；没有像模型端点那样的后台探活。`POST /api/settings/test_embedding` 测的是现在用的那个时也会更新这个状态。

**真机上先验证的顺序**：`bash tests/run_lg_tests.sh`，看 `kb_lc_smoke.py` 三项；然后在内网起 Qwen3-Embedding（README 的"在内网起向量模型"），设置里填好地址，"测试"按钮能算出向量长度；建一个资料库加一个放 SOP 的文件夹，等 `vectors` 追上 `parts`，在检索测试里问一句资料里没有原词的话，看 `via` 里有没有 `vector`。

## 12. 核对数字、深入研究、反馈和标准答案（2026-11-21 补记）

规格见 `docs/两种模式.md` 9.3 到 9.5，形状见 `docs/实施说明.md` 第 22 节。这一轮大部分东西不经过内核，只有下面几处和新内核有关；新内核的测试（`tests/test_deep.py` 的 `LG`）没装包时跳过，**都没有在新内核上运行验证过**。

1. **核对数字挂在 `Runtime.emit` 上**：写完一条不带工具调用的 `assistant_message` 就调 `grounding.after_answer`（同一个线程、同一次 emit 里，所以 `grounding` 事件紧跟在回答后面）。新内核写回答也走 `rt.emit`（`kernel.model_call` 和 `vision_gate`），所以自然带上；假设新内核没有别的地方绕过 `rt.emit` 直接写账本。新内核里带 `tool_calls` 的回答（中间步骤）不核对；**规范化之后**仍然没有调用、但图又继续往下走的情况（理论上不会有）会多一条核对，无害。
2. **深入研究的做法接在用户发言后面**：`context.user_text` 在 `depth == "deep"` 时接上 `context.DEEP_NOTE`；新内核的 `models.human_from_event` 本来就用 `user_text`，所以 HumanMessage 里自然带上，不改系统提示。新内核的压缩（`LedgerSummarization`）摘要的是消息本身，这段做法就在发言里（以"（深入研究：……"开头），所以摘要里能看出来；账本里的 `summary` 事件照旧。
3. **步数上限翻倍**：`lg/middleware.build` 建 `ModelCallLimitMiddleware(run_limit=…)` 时按账本里最后一条用户发言算（`context.step_limit`，翻倍、不超过 60）；"步数用尽"的提示（`host.Runner.invoke`）用同样的算法。图在每次任务线程起来时建（`host.Runner.__init__`），所以**线程还在跑时插进来的 deep 发言，要等下一次起线程才按翻倍算**（旧内核是每一步现算，没有这个差别）。另外 `ModelCallLimitMiddleware` 的 `run_limit` 是"单次 invoke 内"计数（3.8），和旧内核"这一轮"的计数口径本来就不完全一样。
4. **标准答案、反馈、弱命中**都在 `agent/feedback.py`、`agent/kb/` 和接口里，两个内核共用，和内核无关。`kb.engine=langchain` 时向量那一路的分数是 Chroma 的 `similarity_search_with_relevance_scores`（collection 用 cosine，分数约等于余弦相似度），`kb.min_sim` 和 builtin 一样比；如果 Chroma 版本给出的不是余弦相似度，门槛要另调。

## 13. 工具按需加载、重复调用检测；文档摘要的后台线程（2026-11-21 补记）

这一轮在新内核上的改动同样没有运行过（这里没装 LangChain）。下面是"后端·内核"的笔记原文。

做法照规格 3.7：所有工具都登记给工具节点（`lg/tools.to_langchain` 用 `kernel.tools`，即这次能用的全部 + tool_load），在 `KernelMiddleware.wrap_model_call` → `kernel.model_call` → `kernel.filter_tools(request)` 里 `request.override(tools=…)` 过滤：

- 是我们的工具、但所在组没带的去掉；`write_todos`（TodoListMiddleware 加的）原样保留；
- `tool_load` 换成一个新建的 `StructuredTool`（说明里是现在没带的组），全带上了就去掉；
- 只改这一次请求。

依赖的接口和没验证的假设：

1. **`ModelRequest.tools` 是这次要绑定的工具列表，`request.override(tools=…)` 之后 create_agent 按它重新 `bind_tools`**。官方 `LLMToolSelectorMiddleware` 就是这么做的（源码 `langchain/agents/middleware/tool_selection.py`，`wrap_model_call` 里 `request.override(tools=selected)`；文档 https://docs.langchain.com/oss/python/langchain/middleware/built-in 的 "LLM tool selector"）。这次没有重新抓取核对，按上一轮记下的 factory.py 行为推的。如果不重新绑定，模型会看到全部工具（等于没按需加载，不会出错）。测试的假模型 `ScriptedChatModel.bind_tools` 记下工具，`test_lg_toolsets` 会看出来。
2. **`request.tools` 里的元素有 `.name`（BaseTool）或是 dict**（`{"name"}` 或 `{"function": {"name"}}`），`_tool_name` 两种都认。
3. **工具节点按名字执行，和绑定给模型的对象无关**：模型调用了过滤掉的工具（或者用我们新建的那个 tool_load），ToolNode 在它自己登记的工具里按名字找到并执行（经过 `wrap_tool_call` → `run_tool`）。如果 ToolNode 只认这次请求里的工具，直接调用没带的工具会变成"工具不存在"的错误消息，自动加载失效（但 tool_load 之后的正常路径不受影响）。
4. **批准中间件**：`interrupt_on` 按全部工具名建（含 tool_load，它的 `when` → `gate` 判成放行）。被重复调用检测拦下的调用 `gate` 返回 False（不问人）。
5. **压缩阈值**：`SummarizationMiddleware` 的 `trigger` 是建图时按当时带的工具算的；中途加载了一组之后，`token_counter` 改成 `kernel.summary_tokens`，在消息的估算上加上"建图以后多出来的工具定义"。假设 `token_counter` 只被用来数要不要触发和保留多少（文档是这么写的）；`keep` 也会跟着多算这一点，影响很小。
6. **`gate` 和 `run_tool` 各算一次是否重复**：`LoopGuard.check` 不改状态，同一个调用两次结果一样；记录只在 `execute` 真正执行后做。被拦之后又发同样的调用：`run_tool` 里置 `guard_stop`，下一次 `model_call` 一开始发 notice 并 `raise Abort("stop", "paused", "重复调用")`（和"连续失败"同一条路），不在工具节点里抛。
7. **插话**：`model_call` 里 `unfed()` 之后调 `toolset.refresh()`（读账本里比上次新的 user_message），所以 Abort("restart") → feed → 再进 model_call 时会补上新发言的信号。
8. 新内核的 `run_todos`（write_todos）不经过重复调用检测；过渡内核的 todo_write 也豁免，行为一致。

### 资料这一侧没验证的

- **真实模型写摘要**：只用假服务测过。真模型能不能稳定给出 JSON（尤其不开 response_format 时）、150 字的要求守不守、会不会带 `<think>`，要跑 `tests/realmodel/` 的 `card_summary_1..3` 才知道。解析时容忍代码块围栏和 `<think>`。
- **真实模型会不会用卡片**：`card_whole`、`card_which`、`card_then_section`、`card_list_no_cite`、`card_section_answer`、`card_doc_arg` 六个探测，和 e2e 的"一整份文件讲什么""有哪些文件"两个场景，都没跑过（这里连不上模型）。gen.js 用 `node --check` 查过、生成 50 个请求正常；e2e.py 过了 py_compile 和 3.9 语法检查。
- **前台让路**靠 `rt.lives[*].alive`；新内核（`agent/lg/`）是不是也登记在 `rt.lives` 里，我看过 runtime 的 `_start` 两个内核都经它启动，但没在新内核下跑过。
- 写摘要的模型调用用的是端点列表里第一个"不是确定连不上"的端点，不走 capability 的选端点逻辑（上下文大小等）；3,000 token 的请求在 32K 的端点上不成问题。
- 向量签名变了会让**用户电脑上已经算好的向量全部重算一次**（预期行为，规格要求的；大库会花些时间，界面上 vectors < parts 时会看出来）。
- 大库：kb_list 的 query、gaps 去重都是在 Python 里扫一遍（几千份文件、几千条问题以内没问题），没量过上万的情况。
- 中文问题对英文库的关键词检索几乎必然没有命中（评测里那一题就是），提醒只是让模型换英文再查；有向量模型时会好些，没验证。
